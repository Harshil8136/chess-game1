# Working on Windows

> **In plain words.** The owner downloaded the kit to a Windows computer and tried it. `npm
> install` stopped with an error, and once pnpm was installed, `pnpm verify` stopped at its sixth
> check. The kit now runs the same way on Windows as on Linux and macOS, and its README says how
> to start.

## What happened

| What the owner ran | What it said | Why |
|---|---|---|
| `npm install` | `Unsupported URL Type "catalog:"` | The kit is a pnpm workspace. Each package names its third-party versions as `catalog:`, so one version is pinned once for every package, and only pnpm reads that. npm stops while reading the list, before it runs anything, so no message of ours can come first. |
| `pnpm install --frozen-lockfile` | `pnpm` is not recognised | pnpm was not installed yet. `npm install -g pnpm` installs it, and it then switches itself to the version `package.json` names. |
| `pnpm verify` | `FAIL format`, `spawnSync pnpm ENOENT` | The verify chain started its gates by name. On Windows, the `pnpm` on the path is a `.cmd` file, and Node starts only `.exe` files by name without a shell, so every gate that runs pnpm failed before it ran. |

A Windows checkout had a fourth problem waiting: Git for Windows turns LF line endings into CRLF
by default, and the format check, the migration checksums and the identifier scan read files
byte for byte.

## What changed

- **`.gitattributes`**, in this repository and in the client template: every text file is
  checked out with LF on every system.
- **`scripts/lib/pnpm.mjs`**: the verify chain starts a gate that names `pnpm` as this Node
  running pnpm's own script, which pnpm names in `npm_execpath` when it starts `pnpm verify`; a
  gate that names `node` runs on this same Node. Nothing is looked up on the path, so there is no
  `.cmd` to trip on and no shell.
- **`packages/cli/src/tools.ts`**: the command-line tool starts pnpm and wrangler the same way,
  pnpm from `npm_execpath` and wrangler from the repository's own dependency. This covers
  `oltrem doctor`'s pnpm check (which `oltrem setup` runs too), `oltrem migrations apply`,
  `oltrem backup drill` and `oltrem github report`. Other tools (git, age) are real programs on Windows and are still
  started by name.
- **README**: how to install and check the kit on your own computer, and the stale "phase 1" line
  replaced by a link to where things stand.

## Decisions

- **No shell.** Starting a `.cmd` through `cmd.exe` would work, but it joins the arguments into
  one line without escaping them, and the tool passes SQL to wrangler. Running each tool's script
  on Node needs no escaping and no new dependency.
- **pnpm stays.** The plan chose pnpm workspaces with one catalog of versions (plan 15 and its
  research). Whether people should run plain `npm install` and `npm run dev` is the owner's
  question, put on a card in the thread on the same day.

## How it was verified

- The owner's error reproduced here: with no `pnpm` on the path and pnpm started through its
  script, the old verify chain failed at `format` with `spawnSync pnpm ENOENT`; the new one
  passed all twelve gates in 67.4 s.
- `scripts/pnpm.test.mjs`: pnpm's script on this Node when pnpm started the run (a Windows path
  among them), the name when npm or nothing did, and `node` on this Node.
- `packages/cli/test/tools.test.ts`: pnpm the same way; wrangler resolved to the client
  template's own `wrangler/bin/wrangler.js`; other tools by name.
- Not verified here: a run on Windows itself. The owner's next `pnpm verify` on a fresh copy is
  that run.
