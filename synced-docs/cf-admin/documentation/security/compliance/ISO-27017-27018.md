# ISO/IEC 27017 & 27018 Statements

> **TL;DR (non-technical):** Two questions enterprise buyers ask that generic
> "we're secure" answers do not cover: *who is responsible for what* between us
> and our cloud providers (27017), and *how personal data is protected when a
> third party hosts it* (27018). This documents both. Neither is a
> certification — both require ISO 27001 first.

## Context / Scope

Addresses §4.3–4.5 of
[`../../records/reviews/2026-07-22-compliance-certification-audit-all-frameworks-and-roadmap.md`](../../records/reviews/2026-07-22-compliance-certification-audit-all-frameworks-and-roadmap.md),
which recommended documenting 27017 and 27018 *before* committing to an ISO
27001 engagement so both can be scoped into the same Statement of Applicability
from day one — the marginal cost is far lower than adding them later.

**Status: self-assessed, not certified.** 27017 and 27018 are extensions of
27001; no 27001 certification exists for this platform. Nothing here may be
represented as certified.

## Part 1 — ISO/IEC 27017: shared responsibility

### 1.1 Roles

This platform is a **cloud service customer** of Cloudflare, Supabase, Upstash,
Brevo, Resend, Sentry, PostHog, Google (Search Console / PageSpeed) and
OpenRouter, and a **cloud service provider** to its own end customers. The
authoritative list with purposes, data categories and regions is
`../RoPA.md` §3 — nine entries. *(Corrected 2026-09-19: this sentence listed
seven and is now aligned with RoPA and `data-residency.md` §2.)*

### 1.4 Known 27017 gaps

- **No documented exit/offboarding plan per provider** (CLD.8.1.5). If
  Cloudflare or Supabase had to be left, there is no written data-extraction
  and verified-deletion procedure.
- **Shared-resource risk not formally assessed.** Split by store
  *(corrected 2026-09-19)*: D1 `madagascar-db` and R2 `madagascar-images` are
  shared with `cf-astro`; `cf-chatbot` has its **own** D1 (`chatbot-kb`); the
  Supabase project is shared by all three. R2 `arco-documents` belongs to
  `cf-astro`. This is documented in operational terms (see the DR runbook's
  blast-radius warning on Time Travel) but has never been through a formal risk
  assessment.
- **Vendor reports not reviewed on a cadence.** No annual review of
  Cloudflare's or Supabase's SOC 2 reports is scheduled.

## Part 2 — ISO/IEC 27018: PII in public clouds

27018 is the code of practice for a **PII processor** operating in a public
cloud. It is directly on point here: this platform processes customer PII on
infrastructure it does not own.

| 27018 principle | Implementation | Status |
|---|---|---|
| **Consent & choice** | Consent records with a full trail; GPC detected | 🟡 Consumer enforcement lives in `cf-astro` |
| **Purpose legitimacy** | Every activity has a documented basis | ✅ RoPA §2 |
| **Collection limitation** | No PII beyond operational need; **IPs hashed before storage** (`hashIp()` on the D1 write path). The raw IP is used transiently as a rate-limit key at Upstash on session-less routes and is not stored durably. *(Corrected 2026-09-19: "hashed on collection" overstated it by one hop.)* | ✅ |
| **Data minimisation** | `sendDefaultPii: false`; scrubber before Sentry; MIME/size only for ID docs | ✅ |
| **Use/retention limitation** | Per-table retention with a status gate | ✅ `retention-tables.ts` |
| **Accuracy** | Rectification via the ARCO queue | ✅ |
| **Openness/transparency** | PRIVACY.md, RoPA, sub-processor list | ✅ |
| **Individual participation** | ARCO queue with SLA tracking, covered by unit tests | ✅ |
| **Accountability** | Named owner; audit trail; breach runbook | 🟡 IR plan never drilled |
| **Information security** | See SECURITY.md and THREAT-MODEL.md | ✅ |
| **Privacy compliance** | Self-assessed | 🟡 No external audit |

### 2.1 27018-specific obligations

| Obligation | Status |
|---|---|
| Process PII only per customer instruction | ✅ No secondary use; no advertising use |
| **Do not use PII for marketing without consent** | ✅ No profiling; no data sales |
| Disclose sub-processors before engagement | ✅ RoPA §3 |
| Notify the customer of a data breach | ✅ IR runbook §7 |
| Support customer DSAR obligations | ✅ ARCO queue |
| Return/dispose of PII at contract end | 🔴 **Gap** — no documented offboarding procedure |
| Disclose law-enforcement requests unless prohibited | 🔴 **Gap** — no policy, no transparency report |
| Restrict and log administrator PII access | ✅ Audit log; role-gated |
| Secure disposal of media | ✅ (inherited from providers) |

### 2.2 Highest-value 27018 gaps

1. **No customer-offboarding data-return/deletion procedure.** Required by both
   27018 and most enterprise DPAs. A written procedure is days of work and
   would close a question that appears in nearly every security questionnaire.
2. **No law-enforcement request policy.** Cheap to write; conspicuous by its
   absence to a privacy-focused buyer.
3. **No cadence for reviewing sub-processor compliance.**

## Part 3 — Recommendation

Both standards are **documentation exercises given the technical controls that
already exist**, which is exactly why the 07-22 audit recommended writing them
before an ISO 27001 engagement rather than after: folding 27017, 27018 and
27701 into the same Statement of Applicability from day one costs far less than
bolting them on as separate engagements.

**Self-assessed readiness, re-derived 2026-09-19.** The previous line —
"27017 ≈ 75%, 27018 ≈ 80%" — had no derivation anywhere, so it is replaced by
the row counts the reader can check: **§1.3 cloud-specific controls 4 ✅ / 3 🟡;
§2 27018 principles 8 ✅ / 3 🟡; §2.1 27018 obligations 7 ✅ / 2 🔴.** Read those
as a shape, not a score: the two 🔴 obligations (customer offboarding, and law
enforcement requests) are each a single written procedure away, and the 🟡 rows
on audit retention and backup testing are the ones that need engineering rather
than prose. Both standards remain gated on ISO 27001, which is a 🔴 far item
requiring an accredited auditor and 4–9 months.

**Claimable today:** *"We have documented our cloud shared-responsibility model
against ISO/IEC 27017 and our PII-processor obligations against ISO/IEC 27018;
statements available on request."*

**Not claimable:** "ISO 27017 certified" or "ISO 27018 certified" — neither
certification exists, and both require ISO 27001 first.
